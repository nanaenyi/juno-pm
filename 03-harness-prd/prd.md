## Problem & user

RocketShip PMs need this handled: Juno PM is an AI Associate PM embedded in RocketShip’s Slack, Jira and Notion. For this feature it acts as a Monday risk watchdog: it reads, ranks and drafts, and never acts on its own. The human PM owns every decision and every message that leaves the screen.  Task Every Monday at 09:00, Juno scans the past week’s signals and produces the Monday Risk Radar, one screen the PM reads before the 10:00 standup:  The top 3 risks, ranked using RocketShip’s P0–P3 priority framework (Strategy One-Pager), each with source citations and one suggested next step. A NEEDS CLARIFICATION tag on anything the sources contradict or leave vague. A “Routed to you” list for anything involving contracts, legal, regulators, press or customer comms, with sources and no advice. A copy-only standup note draft.. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

Slack: engineering, support and sales channels from the last 7 days (e.g. dev_dave in #backend-monitoring).
Jira: open P0 and P1 tickets, plus anything whose status changed this week.
Notion: the Strategy One-Pager (for P0–P3 ranking rules), the Q3/Q4 Roadmap (what’s committed and what isn’t), and the Engineering Capacity Note (which pod can absorb what).
CRM read-only: the Sales Pipeline Snapshot’s blockers and at-risk flags, used to judge severity only.
Last week’s Radar: from Memory, to show what’s new versus still open.
Excluded:
Personal or HR details (e.g. a team member’s parental leave).
Billing and invoice records.
Customer contact details.
Anything outside the 7-day window unless it’s linked from an in-window item.

**How fresh must it be**

How fresh must it be?
Slack and Jira are re-read live at every run, so the Monday 09:00 Radar reflects everything up to 09:00 that day. Notion docs (Strategy One-Pager, Roadmap, Capacity Note) are re-read at each run too, but they change slowly, so last-edited dates older than 30 days are fine. The CRM pipeline snapshot can be up to 7 days old. The screen header always shows the “as of” time and the last-updated date of each source.

How fast does a change in a source become a change in the answer?
The Radar doesn’t update itself between runs. A change shows up at the next Monday run, or immediately if the PM clicks “Rerun” mid-sprint. Juno never pushes alerts, so a spiraling thread only reaches the PM when they open or rerun the Radar.

What happens when a source is unreachable?
Juno retries the fetch up to 2 times. If it still fails, Juno builds the Radar from the sources it can reach and shows a banner such as “Jira unavailable, risks may be missing.” Any row that depends on the missing source is tagged NEEDS CLARIFICATION, and Juno never fills the gap from Memory or guesses. If Slack and Jira are both down, Juno shows no ranking at all, only the outage notice and last week’s open items, clearly labeled as last week’s.

## 02 Tools · System Capabilities

**The verb list**

Read: Slack search, Jira query, Notion page read, CRM snapshot read.
Write (inside Juno only): draft the Radar screen, draft the standup note, add NEEDS CLARIFICATION tags, add hand-off rows.
Copy-to-clipboard: the PM pastes the note themselves.
No write tools for: Slack posting, email, Intercom, Jira edits or assignment, CRM edits. If a tool isn’t in the harness, Juno can’t misuse it, which enforces Constraint 5 structurally.

**Deliberate omissions**

No Slack post, email or Intercom send tool. Juno outputs drafts only (Constraint 5). Without a send tool, it can’t post even if a prompt or a misread instruction tells it to. The PM copies and sends.
No Jira write or assign tool. Juno is a watchdog, not an executor (Role). Reassigning tickets or moving dates would change team priorities without a human decision.
No CRM write tool, and no customer contact data. Customer comms belong to the human PM (Constraint 4). Without contact details or a CRM write path, Juno can’t draft or send a customer reply, such as to Pearson Co about the 403 error.
No direct query tool on the reporting database. The Engineering Capacity Note says no new scheduled or looped load on the reporting DB until sharding ships in Q4. Juno reads about export failures in Slack and Jira instead of probing the database itself.
No web or press search tool. Press and reporter questions, such as the follow-up on Gavin’s interview, are external comms and go to the PM. Juno doesn’t need outside sources to rank internal risks.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

One scheduled run per Monday. The PM can trigger a rerun mid-sprint.
Up to 2 retries per failed source fetch. If a source is still down, the screen says “Jira unavailable” instead of guessing.
Up to 1 self-check pass on the draft (see Verification). If a row still fails, it is dropped or tagged NEEDS CLARIFICATION. Juno never loops to “resolve” a contradiction.
Hard cap of roughly 50 tool calls per run.

**Latency and cost target**

The Monday run is a scheduled batch job, not a live chat, so it can trade speed for thoroughness. The scheduled run must finish within 5 minutes of its 09:00 start, so the Radar is ready well before the 09:30 read. A mid-sprint “Rerun” should return within 60 seconds almost every time, because the PM is waiting on it.

Cost per run stays predictable because every multiplier is capped:

4 sources, each with up to 2 retries.
1 self-check pass on the draft.
A hard ceiling of 50 tool calls per run.

The worst case is therefore bounded instead of open-ended. Retries and the self-check multiply calls, so Juno never adds a second check pass or extra retries to chase a contradiction. It tags NEEDS CLARIFICATION and stops. A run that hits the 50-call ceiling ships what it has, with a “partial scan” banner, rather than running longer.

## 04 Memory · Data Requirements

**What persists, at what scope**

Keeps:

Last 4 weeks of Radars: top 3 rows, citations and rank.
The PM’s verdict on each row (accepted, dismissed, or edited).
Open NEEDS CLARIFICATION items and hand-off items until the PM closes them.
Recurring-risk counters (e.g. “CSV export: 3rd week in top 3”).

Drops:

Raw thread and ticket text (re-read live each run).
Customer names, contact details and dollar figures beyond what the cited source states.
Drafts the PM discarded.

**Expiry and write rules**

How long each fact lives:

Past Radars (top 3 rows, citations, rank): 4 weeks, then deleted. That’s long enough to spot a recurring risk, and short enough that stale rankings don’t shape new ones.
PM verdicts (accepted, dismissed, edited): 12 weeks, so Juno can learn what this PM tends to dismiss over a full quarter.
Open NEEDS CLARIFICATION and hand-off items: these stay until the PM closes them, with no automatic expiry. Each is resurfaced as “still open, week N” so nothing quietly drops off.
Recurring-risk counters: these reset to zero after 2 weeks out of the top 3.
Raw thread text, customer names and dollar figures: never stored. They’re re-read live from the source at each run.

Who outranks whom:

The PM’s correction always beats Juno’s stored output. If the PM edits a finding, re-ranks a row or dismisses a risk, that version is saved, and Juno’s original is marked superseded rather than kept as an equal.
A live source beats memory. If this week’s Slack or Jira contradicts something stored, the source wins and the memory entry is updated.
A PM correction beats a live source only for that week’s Radar. If the PM’s correction disagrees with a fresh source the next week, Juno doesn’t silently pick one. It shows both and tags the row NEEDS CLARIFICATION.
Only two writers. Memory is written only by the end-of-run save and by PM actions on the Radar screen. Juno can’t rewrite past entries mid-run.

## 05 Permissions · AI Risks & Mitigations

**The permission tier**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | confirm |
| send | blocked |

**Justification**

Without asking:

Read the sources listed in Context.
Rank risks and draft the Radar.
Tag items NEEDS CLARIFICATION.
Copy the draft to the clipboard.

Only with PM approval:

Adding a new source or channel.
Changing the ranking rules away from the P0–P3 framework.
Saving a PM-edited row to Memory.

Never (hand off to the PM):

Posting, sending or emailing anything through Slack, email or Intercom.
Assigning or editing Jira tickets.
Drafting customer, press or reporter replies.
Advising on contracts, legal or compliance matters, such as walking back the Acme promises or SSO compliance.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

Citation check: every claim carries at least one Slack, Jira or Notion reference that resolves and actually contains the claim. Rows without one are moved to Held back: unverified
Number check: every number, name or date on screen appears verbatim in a cited source, so nothing is invented.
Rank check: each row’s severity matches the One-Pager’s P0–P3 definitions. Cosmetic items like dark mode or the bright nav bar can’t rank above P3.
Rule check: no row offers contract, legal, regulator or customer-comms advice. Those must sit in “Routed to you.”
Measures to define in Module 5: % of rows the PM accepts as-is, risks the PM had to add by hand, and time from opening the Radar to standup-ready.

**Failure behaviour**

When a check fails, Juno shows the row in a cautious form and says why, so the PM always sees what was held back and the reason.

Citation check fails (no source, or the source doesn’t contain the claim): the row moves to a “Held back: unverified” section below the top 3, labeled “No source found for this claim.” It never appears as a ranked risk.
Number check fails (a figure, name or date isn’t in the cited source): the number is removed and replaced with “[figure not in source],” and the row is tagged NEEDS CLARIFICATION. Juno doesn’t round, estimate or fill it from memory.
Rank check fails (severity doesn’t match the P0–P3 definitions): Juno shows the row at the rank the framework supports, with a note such as “Ranked P3: cosmetic, no trust or compliance impact.” The PM can override it.
Rule check fails (a row gives contract, legal, regulator or customer-comms advice): the advice is stripped, and the item moves to “Routed to you” with its sources only.
Too many failures (fewer than 3 rows pass): Juno shows only the rows that passed, with a banner such as “Only 2 risks met the evidence bar this week.” It never pads the list to reach 3.
Every failure is logged in the run summary at the bottom of the screen (e.g. “4 claims held back, 1 number removed, 1 item routed”), so the PM can spot patterns and Module 5 has something to measure.
